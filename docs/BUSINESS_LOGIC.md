# Бизнес-логика и её история

Это самая важная часть документации. Почти все сложные баги в этом проекте были не в UI, а в правилах ниже — они недокументированы нигде, кроме кода и памяти того, кто их отлаживал. Если новый программист будет что-то менять в отчётах/встречах/КПИ — сначала прочитать этот файл целиком.

## 1. Типы встреч

Три типа (`meeting_type` в `crm_assigned_meetings`/`crm_conducted_meetings`):
- **Новая** — первая встреча с контрагентом.
- **Повторная** — любая встреча с контрагентом, с которым уже была "Новая" ранее.
- **Крупный лид** — встреча в рамках воронки enterprise-лидов (см. раздел 3). Это отдельная категория, не "Новая"/"Повторная".

Правило (проверено и подтверждено пользователем в разговоре): **если у контрагента уже есть "Новая" встреча, назначать вторую "Новую" на него нельзя** — это ограничение относится к **назначению** новой плановой встречи, а не только к проведению. Классификаторы: `isNewMeetingType`, `isRepeatMeetingType`, `isEnterpriseLeadMeetingType`, `resolveEnterpriseMeetingType` — все в `src/lib/kpiMetrics.ts`.

## 2. Сопоставление план↔факт (`buildMeetingEvidenceIndex`)

**Это единственный правильный способ узнать, "было ли фактически проведено" конкретное плановое событие.** Раньше (до рефакторинга) код искал "любое проведённое событие с датой ≥ дата плана" без учёта того, что оно уже могло быть "использовано" для сопоставления с другим планом. Из-за этого:
- (a) при сохранении план мог неверно перезаписаться из "Новая" в "Повторная";
- (b) старый заброшенный план "занимал" чужой более поздний факт (итог/дата "перетекали" не туда);
- (c) КПИ считались с задвоением одного и того же факта на два разных плана.

Решение — жадный алгоритм one-to-one сопоставления в `buildMeetingEvidenceIndex` (кешируется через `getCachedEvidenceIndex`, `WeakMap`):
1. Сначала пытаемся сопоставить факт и план **в рамках одного отчёта** (тот же `report_id`).
2. Если не нашли — берём ближайшую по дате не занятую пару.
3. Каждый факт может быть "потрачен" только на одно сопоставление.

Все счётчики КПИ (`countConductedNewMeetings`, `countConductedKrupMeetings`, `countConductedNewOrKrupMeetings`, `countAssignedNewOrKrupMeetings`) и функции подсветки в UI (`findSpecificConductedEvidence` в `App.tsx`, `conductedMatchesAssigned`, `hasConductedEvidence`) используют этот общий индекс. **Не пишите новый ad-hoc поиск "факта по дате" — используйте индекс.**

### Известная особенность (не баг): расхождение "Назначено X / Проведено X+1" на стыке месяцев

Причина — "Новая" считается по месяцу **назначения**, а "Крупный лид" считается по месяцу **проведения** в объединённом счётчике `countConductedNewOrKrupMeetings`. Если план был назначен в одном месяце, а фактически проведён в другом (или наоборот для Крупный лид), суммы по двум половинкам функции могут не биться между собой при простом визуальном сравнении "Назначено" и "Проведено" за месяц. Это ожидаемое поведение, а не ошибка расчёта — если пользователь снова спросит про такое расхождение, сначала проверить именно эту причину, прежде чем искать баг.

## 3. Воронка "Крупный лид" (enterprise leads)

Таблица `crm_enterprise_leads`. Жизненный цикл:

1. **Лидоруб** обзванивает базу, находит крупного клиента, передаёт его в круп через `digger_transfer_enterprise_batch` (пачкой, модалка `DiggerTransferModal.tsx`). При передаче можно сразу отметить, что встреча уже назначена (`meeting_requested`).
2. Лид попадает в буфер нераспределённых (`EnterpriseLeadsBuffer.tsx`, `routing_status = 'pending_distribution'`), либо сразу назначается менеджеру админом (`admin_assign_enterprise_lead`).
3. **Менеджер** видит лид в "Мои лиды Крупный бизнес" (`ManagerEnterpriseLeadsPanel.tsx`), берёт его в работу (`manager_take_enterprise_lead_in_work`) — **важно: лиды без назначенной встречи, взятые в работу, должны пропадать из списка "Мои лиды"** (это подтверждённое поведение — было один раз сломано попыткой "оставлять их видимыми", откачено обратно, см. миграцию `20260826110000_revert_manager_enterprise_lead_in_work_visible.sql`). Если понадобится это менять снова — сначала уточнить у заказчика, это уже дважды становилось предметом путаницы.
4. Менеджер проводит встречу и фиксирует итог через `manager_set_lead_meeting_status(lead_id, status, result)` — перед этим клиенту показывается модалка "Итог встречи", куда менеджер обязан вписать результат (иначе лид раньше "проваливался" сразу в "проведено" без итога — это было точечно исправлено).
5. Если лид не подходит — менеджер возвращает его обратно в SMB (`manager_return_lead_to_smb`).
6. Триггеры `trg_sync_enterprise_lead_from_meeting` на `crm_assigned_meetings`/`crm_conducted_meetings` синхронизируют состояние лида, когда встреча редактируется напрямую в отчёте (а не через воронку) — это защита от рассинхрона между "встречей в отчёте" и "статусом лида".

**Экран "Лиды" у админа (`EnterpriseLeadsBuffer.tsx`) сознательно НЕ показывает колонку "Итог встречи"** — она была добавлена, затем явно удалена по просьбе заказчика ("у админа, в лидах нужно убрать этот итог встречи. Именно вот в лидах"). Колонка **осталась** на экране лидоруба (`LeadDiggerLeadsPanel.tsx`) — там она нужна. Не путать эти два похожих списка при доработках.

`EnterpriseLeadsAllPanel.tsx` (полный список у админа) имеет фильтр по месяцу, который фильтрует **по дате передачи** (`transferred_on`), не по дате встречи — так и было явно запрошено.

## 4. "Отдел" сотрудника (`staff_dept`) — замороженный снимок

Проблема, которую решили: если сотруднику меняют роль (например, лидоруб → менеджер) или увольняют/заводят заново, отдел раньше пересчитывался "на лету" по текущей роли из `profiles` — из-за этого **вся историческая отчётность задним числом меняла принадлежность к отделу**. Это ломало ретроспективную аналитику ("сколько сделал отдел лидорубов в мае", если человек с мая стал менеджером).

Решение (`20260918123000_report_staff_dept_snapshot.sql`): у `crm_reports` появилась колонка `staff_dept`, которая **проставляется один раз триггером `trg_stamp_report_staff_dept` в момент создания строки отчёта** и больше не пересчитывается. `resolveReportStaffDept` (`src/lib/staffDept.ts`) сначала смотрит на это замороженное поле и только если оно `NULL` (старые строки до миграции) — падает обратно на текущую роль по `manager_id`.

**Важно на будущее:** идея "уволить + завести нового сотрудника под той же ролью" не решает проблему сама по себе — `fetchAssigneeProfilesApi` фильтрует уволенных (`is_active=false`) из списка сотрудников, и такие отчёты просто попадали бы в `'unknown'` вместо неправильного отдела — то есть другой баг того же рода. Использовать именно снимок в `crm_reports.staff_dept`, а не переусложнять со сменой профилей.

## 5. Комиссия по заказу

`crm_confirmed_orders.commission_amount` считается через `calc_order_commission(amount, is_ktp, mrp)`:
- Тарификация зависит от суммы заказа относительно МРП (значение МРП — глобальная настройка, `crm_settings`, редактируется в `AdminSettingsPanel`) и флага `is_ktp` конкретного клиента (`crm_clients.is_ktp` — "особые" контрагенты с другим тарифом).
- Если у заказа указан `via_bin`/`via_entity_name` (сделка прошла "через" другое юрлицо-посредника) — КТП-статус берётся именно от `via_bin`, а не от прямого контрагента (`crm_order_commission_is_ktp`).
- Массовый пересчёт при смене КТП-флага клиента или МРП: `recalc_order_commissions_for_client_bin`, `recalc_order_commissions_for_month`, `backfill_order_commissions` (для заказов, у которых комиссия ещё не посчитана — кнопка в `AdminSettingsPanel`).
- Менеджерам сумма комиссии заказа теперь **видна всегда** (`showCommission` в `OrdersHistoryDashboard`/`OrderSumCell` в `App.tsx`) — раньше была скрыта, показ включён по явному запросу.

## 6. Заказы: группировка по контрагенту и Excel-экспорт

"Уникальных контрагентов" должно считаться **одинаково** и на экране, и при экспорте — единая функция `groupOrdersByCounterparty` (`src/lib/ordersGrouping.ts`), `.length` от её результата. Ранее было расхождение (74 vs 73) из-за того, что подсчёт на экране и в шапке использовал разную логику группировки — исправлено приведением к одной функции.

Экспорт в Excel имеет два режима, синхронизированных с переключателем вида на экране (`ordersViewMode`):
- "По записям" — `exportOrdersToExcel` (обычный построчный).
- "По контрагентам" — `exportGroupedOrdersToExcel` (одна строка на контрагента). В этом режиме суммы и комиссии форматируются **без пробелов-разделителей тысяч** (`formatMoneyCellPlain`) — это единственное место, где формат чисел отличается от остального приложения, сделано по явному запросу.

## 7. Ежедневный отчёт в Telegram

Edge Function `telegram-daily-report`, две независимые задачи `pg_cron` (см. `docs/DATABASE.md`):
- 18:30 Алматы — основной отчёт (сводка по менеджерам, прогноз на неделю, суммы заказов). Сводка лидорубов **временно отключена** (`DIGGER_SUMMARY_ENABLED = false` в `handler.ts`, флаг, а не удалённый код — чтобы можно было быстро вернуть).
- 18:15 Алматы — отдельное сообщение "🔹 Итоги дня 🔹" (`section: 'results'` в теле запроса, обрабатывается тем же handler'ом через `buildTelegramDailyResultsText`) — короткая сводка по подтверждённым заказам дня/месяца с личным зачётом менеджеров.
- Отправка картинки (PNG-рендер отчёта) была отключена по просьбе заказчика — код рендера (`renderReportPng.ts`) оставлен в `_shared/`, но не вызывается из штатного пути (только доступен через `?preview=png` для отладки).

Оба cron-запуска шлют запрос на **один и тот же** Edge Function URL, различаются только телом запроса (`section`). Авторизация — `x-cron-key` заголовок, сверяется с секретом `TELEGRAM_CRON_SECRET`.

## 8. Блокеры vs work items — не путать

- **`crm_manager_work_items`** ("в работе") — рабочий статус конкретной сделки/контрагента на конкретный день отчёта: `in_work`/`waiting`/`blocked`/`done` + следующий шаг + дедлайн.
- **`crm_manager_blockers`** ("блокеры/стопперы") — отдельная, более простая сущность: свободный текст "почему сделка стоит" по контрагенту, без привязки к дате отчёта. Снятие блокера (`resolve_manager_blocker`) засчитывается в КПИ **дня снятия** (`count_resolved_blockers`), не дня создания.

Это две разные таблицы и разные экраны (`ManagerWorkItemsPanel` vs `ManagerBlockersPanel`) — несмотря на смысловое пересечение названий, в коде они не связаны.

## 9. Передача клиента другому менеджеру — видимость истории без переноса КПИ

Когда контрагента переназначают на нового менеджера (`crm_clients.manager_id` меняется), возникает конфликт двух требований:
- новый менеджер должен видеть **полную историю** заказов по этому контрагенту, включая те, что сделал прежний (в т.ч. уже уволенный) менеджер;
- но эти старые заказы **не должны** засчитываться новому менеджеру в КПИ/суммы за месяц — они физически остаются в отчётах прежнего менеджера.

Просто расширить фронтенд не получится: RLS на `crm_reports`/`crm_confirmed_orders` физически не пропускает в браузер менеджера чужие строки отчётов (см. `docs/DATABASE.md`, раздел RLS) — это не UI-фильтр, а ограничение на уровне базы. Решение — точечный `SECURITY DEFINER` RPC `list_managed_client_orders()`: возвращает заказы по БИН-ам, которые сейчас закреплены за вызывающим менеджером, независимо от того, кто их создал, **не открывая доступ к остальным данным чужого отчёта** (звонки, другие клиенты того же дня и т.д. — только конкретные заказы по конкретному БИН).

На фронтенде (`App.tsx`) результат этого RPC (`managedClientOrders`, только для не-админов) подмешивается в двух местах:
- в список на странице "Заказы" (`allOrdersByDateAndManager`) — с учётом фильтра по датам;
- в окно "История контрагента" (`clientHistoryAggregated.orders`) — по конкретному БИН открытого клиента.

Колонка "Менеджер" в списке заказов, обычно скрытая у не-админов, включается (`showManagerColumn`), если у текущего менеджера есть хотя бы один такой "унаследованный" заказ — иначе будет путаница, чья это продажа. Групповая вьюха "По контрагентам" (`groupOrdersByCounterparty`) уже умеет показывать `"Несколько"` вместо имени менеджера, если в одной группе смешались заказы разных людей.

**Важно:** такие заказы помечаются флагом `OrderRow.isInherited = true` и **исключаются из всех сводных карточек** на странице "Заказы" (`ownOrders` в `OrdersHistoryDashboard` — «Итого сумма по заказам», «Итого комиссия», «Количество заказов», «Уникальных контрагентов»). Изначальная реализация этого не делала — унаследованные заказы просто попадали в общий список, из-за чего сводные суммы на странице заказов у нового менеджера резко подскакивали, хотя реально его собственные показатели не менялись. Строки в самой таблице по-прежнему показывают всё (свои + унаследованные, с именем менеджера у каждой), только верхние итоговые цифры считаются исключительно по своим.
